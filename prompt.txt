# Aufgabe

Entwickle eine vollständige, produktionsfähige, möglichst kleine und schlanke **First-Party-Web-Analytics-Anwendung** für Webseiten und Webapplikationen.

Arbeitsname des Projekts:

**lumly**

Das System soll eine selbst gehostete Alternative zu klassischen Tracking- und Analytics-Lösungen darstellen.

Die Hauptziele sind:

1. extrem einfache Integration in beliebige Webseiten und Webapplikationen
2. möglichst kleines Browser-SDK
3. möglichst umfangreiche und aussagekräftige Analytics
4. Privacy by Design
5. DSGVO- und TDDDG-orientierte Architektur für Deutschland/EU
6. keine Abhängigkeit von Google, Meta oder anderen Tracking-Drittanbietern
7. vollständige Kontrolle über die erhobenen Daten
8. übersichtliches Dashboard
9. leicht erweiterbare Analyseansichten
10. einfacher Self-Hosting-Betrieb

Wichtig:

Behaupte im Produkt und in der Dokumentation **niemals pauschal, das System sei automatisch oder garantiert „DSGVO-konform“**.

Die Rechtmäßigkeit hängt unter anderem von Betreiber, Zweck, Konfiguration, Rechtsgrundlage, Einwilligungsmanagement und Datenschutzerklärung ab.

Baue stattdessen eine Architektur, die datenschutzfreundliche Konfigurationen technisch erzwingt und eine nachvollziehbare Dokumentation der Verarbeitung ermöglicht.

# 3. Zentrales Datenschutzmodell

Implementiere zwei eindeutig getrennte Tracking-Modi.

## Modus A: BASIC / cookieless

Dieser Modus muss ohne persistente Identifikation funktionieren.

Er ist der datenschutzfreundliche Standardmodus.

Er darf insbesondere NICHT verwenden:

* Cookies
* localStorage
* sessionStorage
* IndexedDB
* Fingerprinting
* Canvas Fingerprinting
* WebGL Fingerprinting
* Audio Fingerprinting
* Font Fingerprinting
* persistente Device IDs
* persistente Visitor IDs
* persistente Session IDs
* probabilistische Wiedererkennung
* Hash aus IP + User Agent
* Cross-Site-Tracking

In diesem Modus darf ein Besucher zwischen zwei Seitenaufrufen **nicht wiedererkannt werden**.

Deshalb darf das Dashboard in BASIC auch keine erfundenen Kennzahlen wie „Unique Visitors“ oder „Sessions“ anzeigen.

Nicht ermittelbare Werte werden ausdrücklich als nicht verfügbar gekennzeichnet.

## Modus B: CONSENTED

Dieser Modus wird ausschließlich aktiviert, nachdem die Anwendung eine gültige Analytics-Einwilligung vom Consent-Management der integrierenden Webseite erhalten hat.

Er darf zusätzlich pseudonyme Besucher- und Sitzungsinformationen verwenden.

Beispielsweise:

```text
visitor_id
session_id
```

Diese IDs müssen:

* zufällig erzeugt sein
* ausreichend Entropie besitzen
* keinerlei persönliche Information codieren
* First Party sein
* nach Widerruf der Einwilligung entfernt werden

Verwende niemals Fingerprinting als Ersatz für eine Visitor-ID.

# 4. Consent API

Das Tracking-SDK darf kein eigenes Cookie-Banner voraussetzen.

Stattdessen muss es sich problemlos mit bestehenden Consent-Management-Systemen verbinden lassen.

Biete eine API wie:

```ts
tracker.setConsent("granted");
tracker.setConsent("denied");
tracker.setConsent("unknown");
```

oder:

```ts
tracker.setConsent({
    analytics: true
});
```

Default:

```text
unknown
```

`unknown` und `denied` dürfen ausschließlich BASIC-Tracking erlauben.

Erst `granted` aktiviert CONSENTED.

Beim Wechsel:

```text
unknown -> granted
```

dürfen IDs erzeugt und erweiterte Daten erhoben werden.

Beim Wechsel:

```text
granted -> denied
```

müssen:

* persistente Analytics-IDs lokal entfernt werden
* CONSENTED-Tracking sofort beendet werden
* BASIC-Modus aktiviert werden
* optional eine Funktion angeboten werden, mit der zuvor gespeicherte pseudonyme Trackingdaten gelöscht werden können

Biete dafür beispielsweise:

```ts
tracker.forget();
```

# 5. BASIC-Tracking

Erhebe im BASIC-Modus nur Informationen, die ohne persistente Wiedererkennung sinnvoll auswertbar sind.

Mindestens:

```text
event_id
site_id
event_type
timestamp
page_path
page_title
hostname
referrer_host
referrer_path bei same-origin
campaign_source
campaign_medium
campaign_campaign
tracking_mode = basic
```

Query-Parameter dürfen grundsätzlich NICHT vollständig gespeichert werden.

Standardmäßig:

```text
?email=
?token=
?user=
?session=
?search=
```

und sämtliche unbekannten Queryparameter entfernen.

Nur ausdrücklich konfigurierte Marketingparameter dürfen verarbeitet werden, beispielsweise:

```text
utm_source
utm_medium
utm_campaign
utm_content
utm_term
```

Auch diese:

* auf eine maximale Länge beschränken
* Steuerzeichen entfernen
* keine unbeschränkten freien Werte zulassen

Der Server darf die Quell-IP technisch für die Verarbeitung der HTTP-Anfrage sehen.

Die rohe IP-Adresse darf jedoch niemals in der Analytics-Datenbank gespeichert werden.

Falls Geo-Auswertung aktiviert wird:

```text
IP
 -> transient verarbeiten
 -> grobe Region ermitteln
 -> maximal Land / optional Bundesland speichern
 -> IP verwerfen
```

Geo-Auswertung muss konfigurierbar sein und darf nicht als rechtlich automatisch zulässig dargestellt werden.

Den vollständigen User-Agent nicht speichern.

Falls sinnvoll, serverseitig daraus nur grobe Kategorien ableiten:

```text
browser_family
os_family
device_class
```

Danach den vollständigen User-Agent verwerfen.

# 8. PII-Schutz

Implementiere einen zentralen Sanitizer.

Alle eingehenden Events müssen den Sanitizer passieren.

Er soll verdächtige Property-Namen erkennen, beispielsweise:

```text
email
mail
phone
telephone
password
passwd
token
jwt
auth
authorization
firstname
lastname
fullname
address
street
iban
creditcard
```

Solche Felder werden standardmäßig verworfen.

Zusätzlich einfache Erkennung typischer:

* E-Mail-Adressen
* Bearer Tokens
* JWTs
* Kreditkartennummern

in frei übergebenen Strings.

Der Sanitizer dient als zusätzliche Schutzschicht und darf nicht als perfekte PII-Erkennung dargestellt werden.

# 9. Tracker SDK

Das Browser-SDK ist ein Kernbestandteil des Produkts.

Ziel:

```text
<= 8 kB gzip
```

Hard Limit:

```text
12 kB gzip
```

Falls das Ziel nicht erreichbar ist, dokumentiere die Ursache.

Das SDK darf keine Runtime-Abhängigkeit von React oder anderen Frameworks besitzen.

Eigenschaften:

* Vanilla TypeScript
* tree-shakeable
* kein externes Tracking
* kein CDN-Zwang
* async/defer kompatibel
* Navigation niemals blockieren
* Fehler im Tracker dürfen die Host-Anwendung niemals beschädigen
* `navigator.sendBeacon()` bevorzugen, wo sinnvoll
* ansonsten `fetch(..., { keepalive: true })`
* Events bei Bedarf bündeln
* Fehler intern abfangen
* kein `console.log` in Production

# 14. Collector API

Hauptendpunkt:

```http
POST /api/v1/collect
```

Unterstütze einzelne Events und kleine Batches.

Beispiel:

```json
{
    "site": "...",
    "events": [
        {
            "type": "page_view",
            "timestamp": "...",
            "path": "/produkte",
            "mode": "basic"
        }
    ]
}
```

Grenzen:

```text
max. 20 Events pro Batch
max. Requestgröße ca. 32–64 kB
max. Property-Anzahl
max. Stringlängen
```

Ungültige Events:

* niemals teilweise ungeprüft speichern
* mit nachvollziehbarer Fehlerbehandlung verwerfen

Bei erfolgreicher Annahme genügt:

```http
204 No Content
```

oder:

```http
202 Accepted
```

# 15. Missbrauchsschutz

Der Collector ist öffentlich erreichbar.

Implementiere:

* Allowed-Origin-Prüfung
* Request Size Limits
* Schema Validation
* Property Limits
* Event Type Allowlist
* Rate Limiting
* Bot-/Crawler-Kennzeichnung, soweit zuverlässig möglich
* keine Speicherung der IP für Rate Limiting

IP-basierte Rate-Limit-Informationen nur kurzzeitig im Arbeitsspeicher halten.

Ein öffentlicher Site-Identifier darf niemals als Authentifizierung behandelt werden.

# 18. Retention

Rohdaten müssen automatisch gelöscht werden können.

Konfigurierbare Default-Retention, beispielsweise:

```text
90 Tage
```

Dies ist eine technische Voreinstellung und keine Aussage darüber, welche Speicherdauer rechtlich erforderlich oder zulässig ist.

Implementiere einen Retention Job:

```text
events older than retention_days
 -> chunkweise löschen
```

Nicht personenbezogene, echte Aggregationen dürfen separat behandelt werden.

Retention darf die Datenbank nicht durch einen gigantischen `DELETE` blockieren.

# 48. Vorgehen bei Unsicherheit

Treffe vernünftige technische Entscheidungen selbst.

Frage nicht bei jeder Kleinigkeit nach.

Wenn zwei Lösungen möglich sind:

1. bevorzuge die einfachere
2. bevorzuge weniger Dependencies
3. bevorzuge weniger gespeicherte personenbezogene Daten
4. bevorzuge explizites Verhalten gegenüber Magie
5. dokumentiere relevante Trade-offs

Wenn eine gewünschte Analytics-Funktion nur durch Fingerprinting oder andere problematische Wiedererkennung möglich wäre:

**implementiere sie nicht auf diese Weise.**

Dokumentiere stattdessen die technische Einschränkung.
